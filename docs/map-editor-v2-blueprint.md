# 맵에디터 V2 설계도 — 지형 편집기에서 사물 편집기로 승급

작성: 2026-07-04. 상태: **P1 1차 구현 완료(2026-07-05). P2 팔레트/배치 UI는 아직 미착수.**
승급 선언: V1(현 map-editor.js) = 선과 사각형을 만지는 **개발자용 지형 도구**. V2 = 이름 있는 사물을 팔레트에서 집어 배치하는 **창작 도구**. 이 문서가 V2의 단일 기준이다.

## 0. 왜 승급인가 (한 문단)

사용자가 원하는 그림은 상상이 아니라 선례다: 과거 빌드 "RECLAIM(수복) v6"에 카테고리 팔레트 + 건물 카드 + 자유 배치가 실제로 돌아갔다 (증거: `docs/refs/reclaim-v6-palette.png`). 단, **계승하는 것은 팔레트라는 형식뿐이다.** v6의 분류(경제/국방 등)는 도시 경영용이라 버린다 — 2026-07-04 사용자 결정. V2의 역할은 셋이다: ① AI가 맵 초안을 만들어도 사람이 위치를 자유롭게 재배치, ② 창작마당의 맵 파일 포맷 제공, ③ R3 스토리모드의 도시맵(건물/문/실내) 기반. 셋 다 같은 요구로 수렴한다: **맵의 구성 요소가 "사각형"이 아니라 "사물"이어야 한다.**

## 1. 기초 공사 — 맵 스키마 v1 (모든 것의 선행)

새 파일 `src/data/map-schema.js` + 맵은 JSON으로 저장/교환 가능해야 한다 (창작마당 = 이 파일 포맷).

```json
{
  "schemaVersion": 1,
  "id": "map02-ironline",
  "name": "철선",
  "world": { "width": 3400, "height": 2200 },
  "roads": [ ... ],
  "objects": [
    {
      "id": "obj-000123",
      "type": "tank-base",
      "x": 1200, "y": 800,
      "rot": 0,
      "scale": 1,
      "tags": ["red-spawn-area"]
    }
  ],
  "zones": [ { "id": "cap-A", "kind": "capture", "x": 0, "y": 0, "r": 120 } ],
  "story": null
}
```

스키마 규칙:
- **objects는 인스턴스만 갖는다** (어디에 무엇이). 사물의 성질은 도감이 갖는다 (아래 2절). 인스턴스에 성질을 복사해 넣지 않는다 — 도감 수정이 전 맵에 반영되게.
- `id`는 맵 안에서 유일. AI 초안·수동 편집·게임 런타임이 같은 id로 같은 사물을 가리킨다.
- `story` 필드는 v1에서 항상 null. R3에서 문/실내/스토리노드가 여기 붙는다 — **자리만 예약, 지금 설계 금지.**
- 기존 map01 호환: `obstacles`(kind: concrete/building)를 objects로 자동 변환하는 `migrateV0()` 1개 함수. 기존 맵을 손으로 다시 만들지 않는다.

## 2. 사물 도감 — `src/data/object-catalog.js`

v6의 팔레트 카드가 이것의 원형이다. 항목당:

```js
"tank-base": {
  name: "전차기지",
  category: "건물",            // 건물 | 실내 | 구조물 | 장식 | 바닥 (아래 분류 기준 참조)
  footprint: { w: 220, h: 160 },
  collision: true,
  spriteSlot: "object.tank-base",  // 에셋팩 슬롯 규약 재사용 — 그림 없으면 벡터 대체
  hp: null,                    // null = 파괴 불가. 숫자 = 파괴 가능 (P4에서 활성화)
  cover: "heavy",              // AI 전술맵이 읽는 값: none | light | heavy
  cost: 1710,                  // 선택 필드. 전투맵 에디터는 무시, 도시/스토리 모드가 사용
  interactions: []             // P4 전까지 빈 배열 고정
}
```

분류 기준 (2026-07-04 확정 — 사물의 **종류**로 나눈다. 용도/진영 분류 금지):

| 카테고리 | 담는 것 | 예 |
| --- | --- | --- |
| 건물 | 외형 단위의 건축물. R3에서 문/실내 연결의 주체 | 주택, 상가, 병영, 전차기지 |
| 실내 | 건물 내부 소품 (R3 실내 씬에서 사용, 지금은 도감에 자리만) | 침대, 책상, 계산대 |
| 구조물 | 전장 기능이 있는 설치물·구조체 | 방벽, 모래주머니, 참호, 다리, 초소 |
| 장식 | 상세 장식물. 충돌/엄폐 없거나 약함 | 나무, 가로등, 잔해, 간판, 표지판 |
| 바닥 | 지면 표현 | 아스팔트, 흙, 풀, 도로 패치 |

- 분류는 **팔레트에서 찾기 위한 서랍**이지 게임 규칙이 아니다. 엄폐 성능은 `cover`, 파괴 가능은 `hp`, 진영 관련은 `tags`가 담당 — "국방" 같은 용도 분류가 필요 없는 이유.
- category는 문자열 데이터라 서랍 재편성은 언제든 무비용. 단 용도/진영 이름의 카테고리는 다시 만들지 않는다.

원칙:
- **도감은 데이터 파일이다.** 새 건물 추가 = 도감 1항목 + 그림 1장(선택). 코드 수정 없음. 병과/무기/에셋팩과 같은 사상.
- spriteSlot은 기존 에셋팩 시스템에 슬롯 이름만 추가 — 렌더러 fallback, check-asset-pack 검사, PNG 덮어쓰기 규약 전부 그대로 탄다.
- `cover` 값으로 전술맵(cover nodes)이 자동 생성되게 연결 — AI가 새 맵에서도 즉시 엄폐를 이해한다.

## 3. 에디터 V2 기능 목록 (v6 화면 기준)

필수 (P2~P3):
- 하단 팔레트 바: 카테고리 탭 + 사물 카드(도감에서 자동 생성, 에셋팩 썸네일).
- 배치 / 이동 / 회전 / 삭제 / 복제. 격자 스냅과 충돌 검사는 V1 것 재사용.
- 크기 조절: footprint 핸들 드래그 (scale이 아니라 w/h 조정, 도감 min/max 안에서).
- 다중 선택 + **그룹(합치기 v1)**: 여러 사물을 묶어 한 번에 이동/복제. 기하학적 병합이 아니라 묶음이다 — v6의 "합치는 형태"는 그룹으로 시작하고, 진짜 도형 병합은 요구가 실제로 생기면 그때 설계.
- 실행취소/재실행 (V1에 없음 — V2 필수. 편집 명령을 스택에 쌓는 표준 방식).
- JSON 내보내기/불러오기 (창작마당 포맷). localStorage 초안은 유지.

명시적 제외 (v1 스코프 아님):
- 파괴/재설치 런타임 상호작용 → P4 (게임플레이와 겹침, 별도 게이트)
- 문/실내/스토리노드 → R3
- 실시간 협업 편집, 3D, 타일 지형 페인팅

## 3.5 건물 내부 구현 방향 (2026-07-04 확정 — 에디터 설계의 최대 갈림길)

두 방식을 목적별로 갈라 쓴다:

| | A. 컷어웨이 (지붕 걷기) | B. 텔레포트 씬 |
| --- | --- | --- |
| 구조 | 벽·가구가 바깥과 같은 좌표, 지붕이 덮음. 진입 시 지붕 투명화 | 문 = 씬 전환, 실내는 별도 소형 맵 |
| 쓰는 곳 | **전투맵** (R2) — 실내 총격전, AI 추격, 소탕전이 한 맵에서 | **스토리/도시맵** (R3) — 대화·폰 연출용. baegeum-city-v2 설계 계승 |
| 제약 | 실내 크기 = 건물 실제 크기 | 전투 연속성 끊김 (전장용 실격) |

핵심 원칙 1: **실내 전용 에디터를 만들지 않는다.** 실내 = "건물 footprint 안에 배치된 사물들" (벽=구조물, 가구=실내 카테고리). 같은 스키마, 같은 팔레트, 같은 실행취소 스택.

핵심 원칙 2 (2026-07-04 사용자 결정): **건물은 처음부터 내부가 구현된 완제품으로 배치된다 (프리팹).**
- 도감의 건물 항목이 `interiorTemplate`을 갖는다: footprint 기준 상대좌표의 벽/문/가구 목록. 팔레트에서 놓는 순간 내부가 완성된 채 찍힌다 — 배치 즉시 플레이 가능.
- **문 자동 배치 (유기적 규칙):** 기본값은 템플릿의 문 위치, 배치 순간 가장 가까운 도로를 바라보는 면으로 자동 회전. 도로가 없으면 템플릿 기본값.
- **씨앗 변형:** 템플릿당 가구 배열 변형 2~3종, 사물 id를 씨앗으로 결정적 선택 (배금도시 `random.js` 방식). 같은 집 복붙 느낌 방지, 저장/재현 가능.
- **수동 조정 = 덮어쓰기(diff):** 더블클릭 → 실내 편집 모드(지붕 숨김 + 팔레트 실내 서랍 + footprint 범위 잠금). 저장되는 것은 템플릿과 달라진 부분만(`overrides`). 안 건드린 건물은 순수 템플릿 참조 — 맵 파일 최소, 도감 개선이 전 맵에 전파.

스키마 추가분 (건물 인스턴스 — 자동일 때 최소, 손댄 만큼만 커짐):
```json
{
  "id": "obj-00042", "type": "house-small", "x": 900, "y": 600,
  "interior": { "mode": "open", "variantSeed": "auto" },
  "overrides": null
}
```
- 문/벽/가구의 실체는 도감 `interiorTemplate`에 있다. `overrides`는 손댄 항목의 diff 목록 (문 이동, 가구 추가/삭제).
- 문은 벽 충돌·시야 차단에 구멍을 내는 지점. AI 경로탐색과 전술맵이 진입로로 읽는다.
- `interior.mode`: `"open"`(컷어웨이, 전투맵 기본) | `"scene"`(텔레포트, R3에서 sceneId 추가) | 생략(내부 없음 — 통짜 건물, 현 obstacle과 동일).
- 콘텐츠 비용 정직하게: 건물 종류당 실내 템플릿 1개는 사람(또는 AI)이 설계해야 한다. P2.5 데모는 템플릿 1종(방 2개 집)으로 시작.

**유기적 연결 규칙 (2026-07-04 확정):**
- **도로:** 끝점을 다른 도로 근처로 끌면 스냅 + 교차로 자동 생성. V1의 `collectRoadJunctions`/점 결합을 계승해 명문화 — 신규 개발 아님.
- **건물:** 두 footprint가 일정 길이 이상 맞닿으면 에디터가 공유 벽에 통로(개구부)를 자동 제안/생성. 삭제 가능(overrides diff). 연결 기록은 `{ from: "obj-A", to: "obj-B", wall: ..., offset: ... }` 한 줄.
- **철칙: 연결은 융합이 아니라 문이다.** 실내 템플릿을 기하학적으로 병합하지 않는다 — 각 건물의 템플릿·씨앗·overrides는 독립으로 유지되고, 연결은 통로 레코드만 추가한다. (융합은 템플릿×변형×덮어쓰기 상호작용으로 복잡도 폭발 — 금지.)
- 게임플레이 수확: 붙여 지은 건물 블록의 내부가 이어져 AI 우회 기동·소탕전 성립. 전술맵이 통로를 진입로 노드로 읽는다.
- 단계: 도로 스냅 = P2. 건물 통로 = P3 (그룹 기능과 같은 단계 — "합치기"의 실체가 이 둘이다).
- 렌더러 요구 2개: 사물 z-레이어(바닥<가구<유닛<벽 상단<지붕), 지붕 투명화(footprint 안 점 판정). `src/systems/map-objects.js` 담당.

단계 배치: 문+벽 충돌+지붕 투명화 = **P2.5** (팔레트 배치 다음, 크기조절 전). 가구 실내 서랍 채움과 scene 모드는 R3. 첫 검증: 방 2개짜리 집 1채에서 AI 보병이 문으로 진입해 실내 교전이 성립하는가.

## 4. AI 협업 파이프라인 (이 스키마가 존재하는 이유)

```text
AI: 맵 JSON 초안 생성
    ├─ 교전 예산 준수: 시야선 500~700px, 엄폐 간격 30~60px, 첫 접촉 25~35초
사람: 에디터 V2로 열어 팔레트/드래그로 재배치
검증: tools/check-map-schema.cjs (스키마·id 중복·경계 검사)
      + node tools/check-battlefield-tempo.cjs 를 해당 맵으로 실행 (템포 게이트)
```

- 1호 맵 "철선"(가로 진격전, A-B-C 3레인)이 이 파이프라인의 첫 검증 케이스 (R2 백로그 결정 그대로).
- `check-map-schema.cjs`는 창작마당 업로드 검증기로 재사용된다 — 같은 검사기 하나로 내 맵도 남의 맵도 검사.

## 5. 파일 경계 (래칫 준수 — structure-debt-ratchet-blueprint.md와 한 세트)

## 6. 구현 순서 (단계마다 게이트, 한 번에 하나)

| 단계 | 내용 | 완료 조건 (검증 가능) |
| --- | --- | --- |
| P1 | 스키마 + 도감 + migrateV0 + 게임이 objects 렌더 | map01가 변환 로딩되어 기존과 동일하게 플레이됨, check-map-schema 통과 |
| P2 | 팔레트 + 배치/이동/삭제 + JSON 저장/불러오기 | 새 맵을 팔레트만으로 만들어 저장→게임에서 플레이 가능 |
| P3 | 크기조절/회전/그룹/실행취소 | 실행취소 20회 왕복에 상태 손실 없음 |
| P4 | 파괴 가능 사물 (hp, 잔해) | 별도 게이트 — explosion-impact-plan.md와 합류 |
| P5(R3) | story 필드 활성화 (문/실내/노드) | 스토리모드 설계와 함께 |

P1+P2가 "승급"의 실체다. P1 없이 P2를 시작하는 것 금지 (v6이 죽은 경로).

## 2026-07-05 P1 1차 구현 기록

- 추가 파일: `src/data/object-catalog.js`, `src/data/map-schema.js`, `src/systems/map-objects.js`, `tools/check-map-schema.cjs`.
- `object-catalog.js`는 기존 `scenery-catalog.js`를 읽어 건물/구조물/장식 도감 항목을 만든다. `supply-locker`와 현재 구현명 `supply-crate`도 구조물 항목으로 등록했다.
- `map-schema.js`는 `migrateV0()`로 기존 `world.obstacles`를 `objects` 인스턴스로 변환하고, 런타임에서는 다시 `obstacles`를 재생성한다. 기존 AI/물리/렌더 경로는 그대로 유지한다.
- 레거시 장애물은 크기가 제각각이므로 P1 변환에서는 `w/h`를 배치 크기(transform)로 보존한다. 충돌/엄폐/파괴 가능 같은 성질은 도감에서 읽는다.
- `map01.js`와 `map01-custom-layout.js` 로딩 뒤 `normalizeMapObjects(..., { remigrate: true })`를 호출한다. 최종 커스텀 map01 기준 `objects` 36개와 runtime `obstacles` 36개가 일치한다.
- `npm run map:schema`: `Map schema check passed: {"mapId":"map01","schemaVersion":1,"objects":36,"runtimeObstacles":36,"zones":4,"catalogEntries":14,"warnings":[]}`.
- `npm run check`에 `tools/check-map-schema.cjs`를 추가했다.
