# 스토리모드 × 온라인 융합 진단 — 배금도시 v3 / 수복 R1 자산 실사

작성: 2026-07-04. 요청: "배금도시 v3를 스토리모드로 확장 + 수복 R1(문서 폴더)의 온라인 구조를 참고해 더 정확한 온라인 시스템" 에 대한 상세 진단.

> 결론 먼저: **둘 다 실현 가능하고, 이미 절반은 만들어져 있다.**
> 배금도시 v3에는 폰/주식/장면 엔진이 **작동하는 코드로** 존재하고,
> 수복 R1 폴더에는 Cloudflare Workers + Durable Object 기반 **권위 서버가 실제로** 존재한다.
> 다만 순서는 바뀌면 안 된다: **수복 R1 출시 게이트(G1~G4) 완주 → 온라인 R2 재설계 → 스토리모드.**

## 2. 진단 A — "더 정확한 온라인": 무엇을 가져오고 무엇을 버릴 것인가

### 가져올 것 (특이점레이스 워커에서)
1. **권위 구조 자체**: 방 상태를 서버(DO)가 소유하고, 클라이언트는 입력만 보내고 스냅샷만 받는 계약. 수복의 "클라이언트가 자기 상태를 POST" 구조와 정반대이며, 이게 치트/불일치/스터터의 근본 해법.
2. **방 수명주기 규칙 세트**: 방 코드, 호스트 토큰, 생성 쿨다운, 빈 방 자동 삭제, 종료 후 정리. 수복 room-registry가 파일+톰스톤으로 흉내내는 걸 검증된 규칙으로 교체 가능.
3. **입력 위생**: 초당 입력 제한, 오래된 입력 폐기, 자기 속도 상한. 수복 온라인 안정화 문서들이 겪은 stale-hit/중복 이벤트 문제의 상당수가 이 계층에서 예방됨.
4. **틱/스냅샷 분리 리듬**: 시뮬 100ms 틱 + 스냅샷 브로드캐스트 분리. 수복의 worldstate cadence 실험(p0-10 계열)과 같은 문제의식의 완성형.

### 그대로 못 가져오는 것 (정직한 한계)
- 특이점레이스는 **러너 50명 = 상태가 작음**. 수복 전장은 보병 수백 + 전차 + 탄도 + 전술맵이라 상태가 수십 배. Durable Object는 CPU 시간 제한이 있어서 **전장 시뮬 전체를 DO 안에서 돌리는 건 검증 없이는 못 박는다.**
- 현실적인 R2 온라인 선택지는 둘:
  - **(1) 호스트 권위 + DO 릴레이**: 방장 클라이언트가 AI/전장 시뮬을 돌리고, DO는 방 관리 + 입력/스냅샷 중계 + 검증만. 구현 가장 빠름, 방장 핑/치트가 약점.
  - **(2) DO 서버 시뮬 + AI 다이어트**: 서버가 시뮬을 소유하되 온라인 모드의 AI 수/틱을 낮춤(예: 15v15, AI LOD 강제). 정확하지만 성능 게이트 통과가 선행 조건.
- 판단: **R2 첫 패스는 (1)로 시작하고, `software-foundation-scale-editor-plan.md`의 성능 분해 계측이 끝난 뒤 (2)를 재평가.** 어느 쪽이든 특이점레이스의 방/입력/스냅샷 계약은 공통 기반으로 재사용.

### 지금(R1) 할 일
- 없음. R1은 현 HTTP 구조로 출시. 단, **이 문서를 R2 온라인 재설계의 출발점으로 고정**하고, R1 코드에서 "클라이언트 상태 POST" 경로에 새 기능을 더 쌓지 않는다.

## 3. 진단 B — 스토리모드: 배금도시 v3를 어떻게 흡수하나

### 구조 판단
스토리모드 = **배금도시 폰/일상 계층(전쟁 전)** + **수복 전장 엔진(전쟁 후)** 를 하나의 시나리오 그래프로 잇는 것. 억지 통합이 아닌 이유:
- 배금도시 game/은 이미 장면=데이터, 폰 앱=모듈로 분리되어 있어 **렌더러만 수복 쪽에 맞추면 계층째 이식 가능.**
- baegeum-city-v2 기초 문서가 이미 "Iron Line 맵 기반 도시 + NPC 배회 + 건물 입장"을 설계해둠. 즉 **도시 씬 ↔ 전장 씬이 같은 맵 스키마를 쓰는 그림이 선행 문서로 존재.**
- 00_core의 제1원칙(시스템창 금지, 폰 알림으로 압박)은 수복 스토리모드의 UI 원칙("텍스트 다이어트")과 같은 철학.

### 스토리모드 데이터 경계 (v0 초안)
```text
Scenario   장면 그래프: city-scene | phone-scene | battle-scene | cutscene
Character  이름/관계/기억/생존 상태 — 도시 NPC와 전장 분대원이 같은 ID를 공유
PhoneState 메시지/주식/커뮤니티/뉴스/부재중 — 배금도시 phone.js 상태를 스키마화
WorldEvent 개전/공습/통신두절/피난/점령 — PhoneState와 battle-scene을 잇는 트리거
MapSchema  전투맵 + 민간 장소(건물/문/실내) — 수복 맵에디터가 둘 다 편집
AIState    분대원/민간인/의무병 판단 상태 — 침대전투/후송 계획과 연동
```
핵심 규칙 하나: **도시에서 만난 인물이 전장에서 분대원으로 재등장하려면 Character ID가 두 엔진에서 같아야 한다.** 이것만 지키면 나머지는 나중에 붙일 수 있다.

### 시나리오 스케치 (한국 스토리, 검증용 1화 분량)
1. 도시 씬: 알바 퇴근, NPC 대화 2~3명 (배금도시 장면 데이터 형식).
2. 폰 씬: 주식창/커뮤니티/메시지 (phone-stock/social 이식).
3. WorldEvent `war-breaks-out`: 공습 경보 → 주식 폭락 → 지도앱 먹통 → 부재중 전화.
4. 전장 씬: 수복 엔진으로 전환, 도시에서 만난 인물이 분대원으로 등장.
5. 사망 시: 침대전투 계획의 사망 UI(사망/원인/메인화면)와 동일한 흐름.

## 4. 순서와 게이트 (제일 중요)

```text
[지금]   R1 게이트 완주 (r1-release-gate.md G1~G4) — 스토리모드 코드 금지
[R1 후]  성능 분해 계측 + 맵 스키마 v1 (software-foundation-scale-editor-plan.md)
[R2]     온라인 재설계: 특이점레이스 계약 이식, 호스트 권위 릴레이 첫 패스
[R2~R3]  맵에디터에 민간 장소 메타데이터 추가 (baegeum-city-v2 기초 문서 재활용)
[R3]     스토리모드 v0: 위 1화 분량 시나리오를 세로로 한 번 관통 (폰 1개 앱 + 전투 1판)
```

방어 규칙 (restart 반사 차단):
- 스토리모드/온라인 재설계 어느 것도 **R1 게이트 항목이 전부 닫히기 전에는 코드로 시작하지 않는다.**
- 배금도시 v3 리포는 건드리지 않는다. 이식은 R3 시점에 **복사해서** 가져온다 (원본은 소설 리포로 보존).
- 새 엔진을 만들지 않는다. 특이점레이스 워커, 배금도시 phone.js, 수복 전장 엔진 — 셋 다 이미 있는 코드의 재사용이 원칙.
